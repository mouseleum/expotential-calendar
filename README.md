# Expotential Calendar

Internal trade-show database: ~8,200 shows scraped from public calendars
(Tradeshow Calendar, EventsEye, Expo Exhibition Stands, Informa Markets,
RX Global, plus per-venue sites), merged, deduplicated, and classified by
industry segment and audience (B2B/B2C). The frontend is a React + Vite
single-page table with filters for country/region, venue, industry, audience,
source, date range, and ISO week, plus CSV export, per-user flags
(localStorage), and team-shared extras backed by Vercel KV: manual show
entries, per-show industry overrides, and saved filter presets.

## Running

```sh
npm install
npm run dev        # Vite dev server (the /api/* endpoints need `vercel dev`)
npm run build      # production build to dist/
npm run lint
npm test           # vitest unit tests (date/filter utils, merge helpers, API validation)
```

Deployed on Vercel; `api/` contains the serverless endpoints and `vercel.json`
sets edge caching for `/shows.json`. The table has a calendar-view toggle,
and every view is shareable — filters serialize into the URL (`?f=…`), with a
"Copy link" button in the stats bar. Filtered shows export as CSV or as
all-day `.ics` calendar events. A "what's new" panel in the header shows what
each data refresh added, changed, or dropped. Team-shared state (manual shows, industry
overrides, filter presets, show flags) lives in Vercel KV. If the `WRITE_TOKEN`
env var is set on Vercel, mutating API calls require it (`x-write-token`
header); the UI prompts for it once and remembers it in localStorage.

CI (`.github/workflows/ci.yml`) runs lint + tests + build on every push. Data
refreshes itself weekly via `.github/workflows/refresh-data.yml` (Mondays
05:00 UTC, or Actions → "Refresh data" → Run workflow); classification steps
run when the `ANTHROPIC_API_KEY` repo secret is set. The pipeline aborts
rather than committing bad data when a scrape returns zero results or the
merged dataset shrinks >30% (`ALLOW_SHRINK=1` overrides).

## Data pipeline

Shows are refreshed by the weekly Action (or by hand, below) and committed — the app just serves
`public/shows.json`:

```sh
npm run scrape             # Tradeshow Calendar → data/tradeshow-calendar-raw.json
npm run scrape:expostands  # → data/venue-scrapes/expostands.json
npm run scrape:eventseye   # → data/venue-scrapes/eventseye.json
npm run scrape:eventseye:links  # fills in each show's official website
npm run classify:industry  # Haiku-tags industry segments (needs ANTHROPIC_API_KEY)
npm run classify:audience  # Haiku-tags B2B/B2C audience   (needs ANTHROPIC_API_KEY)
npm run merge              # dedupe + normalize → data/shows.json + public/shows.json
```

Only `data/shows.json` is committed; the served `public/shows.json` copy is
regenerated by the pipeline scripts and by `predev`/`prebuild`.

EventsEye's listing pages never carry a show's website — only its detail
page does. `scrape:eventseye:links` fetches each show's detail page once and
caches the result in `data/eventseye-official-links.json` keyed by detail
URL, so a normal weekly refresh (run automatically, see below) only fetches
pages for shows seen for the first time.

`scripts/merge.js` does cross-source dedup (diacritic-aware name/city/date
matching), venue-name canonicalization (`scripts/venue-aliases.json`),
rule-based industry tagging (`scripts/industry-rules.json`), and Scan2Lead
reference-fair tagging (`scripts/scan2lead-names.json`). Ambiguous merges land
in `data/review-needed.json` for manual review.

Every show is also tagged `major_city` (`scripts/lib/major-cities.js`) —
whether its city is among its country's busiest trade-show cities — backing
the sidebar's "Major cities only" filter, which cuts the long tail of
one-off small-town shows. Fully automatic (no curated list to maintain):
tunable via the `topN`/`minShare` constants in that file.

## Exhibitor lists (List column)

The **List** column queues a run of
[exhibitor-browser-agent](https://github.com/mouseleum/exhibitor-browser-agent).
That is a local worker that uses Claude and a Playwright browser to collect a show's full exhibitor list into a CSV on the machine it runs on.

- Click `⇩` on a row and give the URL of the show's exhibitor list page. The prompt starts with the show's website, or the URL used last time.
- `api/exhibitor-jobs.js` creates or reuses an `events` row and inserts an `extraction_jobs` row with `agent='browser'`, in the Supabase project shared with exporepoapi.
- It remembers the latest job per show in KV hash `exhibitor-jobs`.
- The cell polls until the job finishes: `…` queued → `⟳` running → `✓ N` / `! N` (partial) / `✕` (failed). The tooltip shows the CSV path or the error.
- Needs `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` on Vercel, plus exporepoapi migration `0010_extraction_jobs_agent.sql`. Without them the column stays hidden.

## Supabase copy (calendar_shows) and the MCP server

The merged shows are also upserted into the `calendar_shows` table of the
Supabase project shared with exporepoapi (ref `hihhgpzcklusonxnbfcn`, schema in
exporepoapi `db/migrations/0012_calendar_shows.sql`). The website still reads
`/shows.json`; Supabase is the shared copy other tools query, starting with the
read-only `expo-calendar-mcp` server (see exporepoapi's README).

`src/types/show.ts` is the zod schema for `data/shows.json`. The site
(`src/App.jsx`) and the import script both use it, so field names can't drift.

```sh
npm run import:calendar -- --dry-run  # validate + map, write scripts/out/calendar-import-log.csv
npm run import:calendar               # upsert into calendar_shows (needs .env, below)
npm run link:events                   # link shows to exhibitor-list `events`
npm run link:apply                    # apply hand-confirmed links from the review CSV
```

Needs a local `.env` (gitignored; never in Vercel):

```
SUPABASE_URL=https://hihhgpzcklusonxnbfcn.supabase.co
SUPABASE_SERVICE_ROLE_KEY=...
```

The weekly refresh runs the same two steps after classification when the
`SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` **repository secrets** are set
(Settings → Secrets and variables → Actions). Without them the step is skipped
and only the JSON is updated.

**Keys.** One row per edition, unique on `(series_key, edition_year)`.
`series_key` is the slugified name with any year removed (`ISE 2027` → `ise`);
`edition_year` is the year of `start_date`. Fallbacks, all logged to
`scripts/out/calendar-import-log.csv`:

| reason | what happens |
|---|---|
| `duplicate` | same series + year, start dates ≤ 3 days apart (a dedupe miss) — the richer row is kept, the other skipped |
| `city_suffixed` | the series has several editions a year in different cities — every edition gets the city: `s-factory-expo-shanghai` |
| `half_year_suffixed` | twice a year in the same city — `-h1` (Jan–Jun) / `-h2` (Jul–Dec): `formex-stockholm-h2` |
| `ambiguous`, `no_city` | still can't be told apart — skipped |
| `name_year_mismatch` | the year in the name differs from `start_date` — imported with `start_date`'s year |

Rows missing from a later run are never deleted: they keep their old
`last_seen_at` and are counted in `calendar_scrape_runs.rows_missing`.

Derived columns: `country_code` is filled from the country name when the
scrape has none; `date_status` is `confirmed` when any source is a venue or
organiser site (Stockholmsmässan, Kistamässan, Malmömässan, Bella Center,
Informa, RX) and `listing_only` otherwise; `frequency` and `organiser` come from
`notes` and the sources.

**Linking to exhibitor lists.** `link:events` sets `calendar_shows.event_id`
when a show and an `events` row have the same normalised name (year stripped)
and the same year, one-to-one. Near matches (trigram similarity ≥ 0.6) go to
`scripts/out/event-link-review.csv`: put `y` in `confirm` and run
`npm run link:apply`. The weekly refresh re-runs the matching, so new lists get
linked as they arrive.

**Keep-alive.** `.github/workflows/supabase-keep-alive.yml` calls the MCP
server's `search_shows` (limit 1) every Thursday so the free-plan project
isn't paused for inactivity. Remove it after moving to Pro.
